**Goal:** เพิ่มความสามารถ "ช่วยคิด" ให้หน้า `/surveys/field` (เว็บ) ลดข้อมูลตกหล่นและเร่งการกรอก โดยใช้ **API ฟรี หรือไม่ใช้ API ภายนอกเลย** เป็นค่าเริ่มต้น

## หลักการ

1. **เฟส 1–3 ไม่ใช้ API ภายนอก** (กฎในโค้ด + ความสามารถของ browser) — ฟรีจริงและไม่ส่งข้อมูลลูกค้าออกนอกระบบ
2. **AI/LLM เป็นเฟสท้ายและปิดไว้เป็นค่าเริ่มต้น** เพราะ free tier มีเงื่อนไขเรื่องข้อมูล (ดู "เงื่อนไข API ฟรี")
3. **แอป Flutter (ADR 0030) เป็นเครื่องมือภาคสนามหลัก** และมี offline outbox, วัดด้วยเลเซอร์/รูป/ARCore/LiDAR, Quick Estimate หน้างานอยู่แล้ว → เว็บไม่ทำซ้ำ: ไม่ทำ offline เต็มรูปแบบ ไม่ทำวัดจากภาพ ไม่ทำราคาประมาณ
4. กฎธุรกิจอยู่ที่ Backend; เว็บแสดงผลจาก structured metadata ห้าม parse string ดิบ (AGENTS.md หมวด 7)
5. Reuse First: สิ่งที่นำไปใช้ซ้ำได้ (draft recovery, speech hook) สร้างเป็น hook กลางใน `frontend/src/hooks/` และเสนอผู้ใช้ก่อนลงมือ

## เฟส 1 — ตัวตรวจความครบถ้วน/ความสมเหตุสมผล (ไม่ใช้ API)

> **สถานะ (2026-11-02):** แบ่งเป็น **1a ลงมือแล้ว** = กฎความครบถ้วน (ไม่มีขนาด, ขาดกว้าง/ลึก/สูง, ไม่มีรูป) ใน `schemas/field-survey-checks.ts` + modal เตือนที่ไม่บล็อก; **1b ยังไม่ทำ** = กฎความสมเหตุสมผลของค่า (ช่วงสูงสุด/หน่วยผิด) เพราะ Backend ยังไม่มีขีดจำกัดใดเลย (reference-data hardcode ใน controller และไม่มี range validation) ต้องให้ Survey Owner กำหนดค่า + เพิ่ม `measurementLimits` + sync OpenAPI/generated client ทั้งเว็บและมือถือ (คำถามเปิด #2)

**ปัญหาที่แก้:** รายการขนาด 0 ถูกบันทึกเงียบๆ, ห้องไม่มี measurement, ไม่มีรูป, หน่วยผิด (เมตรกรอกเป็น มม.)

- ผลลัพธ์เป็นรายการ `warnings` แบบมี `code` + `itemId` + `field` ไม่ใช่ข้อความดิบ; ข้อความแสดงผ่าน i18n th/en
- **ไม่บล็อกการบันทึก** (ผู้สำรวจอาจตั้งใจบันทึกบางส่วน) แต่แสดงสรุปก่อนบันทึกและให้ยืนยัน
- ขีดจำกัดค่า (เช่น สูงสุดที่สมเหตุสมผล) ส่งจาก `GET /api/v1/surveys/reference-data` ไม่ hardcode ในเว็บ → **ต้องเพิ่มฟิลด์ใน Backend** (คำถามเปิด #2)

| ไฟล์ | งาน |
| --- | --- |
| Create `frontend/src/features/surveys/lib/field-survey-checks.ts` | ฟังก์ชันบริสุทธิ์ `evaluateFieldSurveyItems(items, limits)` คืน warnings |
| Modify `.../field/field-survey-workspace.tsx` | เรียกตรวจก่อนบันทึก, แสดงสรุปด้วย `Alert`/Modal ยืนยัน |
| Modify `backend` survey reference-data projection + contract doc | เพิ่ม `measurementLimits` |
| `frontend/src/messages/th.json`, `en.json` | ข้อความเตือนครบสองภาษา |

## เฟส 2 — กู้ฉบับร่างบนเว็บ (ไม่ใช้ API)

**ปัญหาที่แก้:** แท็บปิด/รีเฟรช/เน็ตหลุดแล้วข้อมูลที่ยังไม่บันทึกหาย

- Hook กลาง `useDraftRecovery(key)` ใช้ **IndexedDB ของ browser** (ไม่เพิ่ม dependency; รูปเก็บเป็น Blob)
- key = `userId + opportunityId`; หมดอายุ 7 วัน; ล้างเมื่อบันทึกสำเร็จและเมื่อ logout (กันเครื่องใช้ร่วมกัน)
- เปิดหน้าแล้วมีฉบับร่าง → แถบ "กู้ข้อมูลที่ยังไม่ได้บันทึก / ทิ้ง" ไม่กู้เองอัตโนมัติ
- ขอบเขตจำกัดโดยตั้งใจ: ไม่มี sync ไม่มี conflict (งานภาคสนามจริงใช้แอป Flutter)

- [ ] เสนอ Global Reuse ต่อผู้ใช้ → [ ] hook → [ ] ต่อ workspace → [ ] i18n → [ ] tsc/eslint

## เฟส 3 — สรุปงานอัตโนมัติแบบกฎ (ไม่ใช้ API)

สร้างร่าง `scopeSummary`, `assumptions`, `missingDetails` จากรายการ/สไตล์/หมายเหตุด้วยเทมเพลตตายตัว (นับรายการต่อหมวด, รายการที่ไม่มีขนาด/รูป = missingDetails) ผู้สำรวจตรวจและแก้ก่อนบันทึก

- ทำที่ฝั่ง Backend หรือฟังก์ชันบริสุทธิ์ฝั่งเว็บก็ได้ (คำถามเปิด #3); ห้ามเขียนทับข้อความที่ผู้ใช้พิมพ์เอง
- ข้อความ template ผ่าน i18n; ห้ามฝัง Thai ลง payload แบบ hardcode (ปัจจุบันมีใน workspace — ควรเก็บกวาดในเฟสนี้เฉพาะจุดที่แตะ)

## เฟส 4 — พิมพ์ด้วยเสียงเป็นรายการ (Web Speech API — ฟรี ไม่ต้องมี key)

- ปุ่มไมค์ในการ์ดรายการ → ถอดเสียง `th-TH` → **parser แบบกำหนดตายตัว** (คำบอกมิติ กว้าง/ลึก/สูง, หน่วย เมตร/ซม./มม., เลขไทยแบบคำ) → แสดงชิปให้ยืนยันก่อนเติมลงฟอร์ม ไม่เติมเอง
- ตรวจ `SpeechRecognition`/`webkitSpeechRecognition` ตอน runtime; ถ้าไม่รองรับให้ซ่อนปุ่ม
- ข้อควรระวัง: Chrome/Edge ส่งเสียงไปประมวลผลที่เซิร์ฟเวอร์ผู้ให้บริการ browser, Safari ส่งไป Apple และต้องเปิด Dictation; **การรองรับภาษาไทยยืนยันไม่ได้จากเอกสาร ต้องทดสอบบนเครื่องจริง** → แสดงข้อความแจ้งผู้ใช้ก่อนใช้ครั้งแรก
- Flutter ใช้ปลั๊กอินแยก (แผนอื่น)

## เฟส 5 (ทางเลือก) — ขัดเกลาสรุปด้วย LLM ฟรี

- Backend port `ISurveyNarrativeProvider` มี implementation ค่าเริ่มต้น = ตัวสร้างแบบกฎจากเฟส 3; adapter LLM เป็น option ใน config + feature flag **ปิดเป็นค่าเริ่มต้น**
- เรียกจาก Backend เท่านั้น (ห้ามใส่ key ในเว็บ), timeout สั้น, rate limit ต่อผู้ใช้, fallback ไปแบบกฎเมื่อพลาด, บันทึก audit ว่าใช้ผู้ให้บริการไหน
- ส่งเฉพาะข้อความที่ตัดข้อมูลระบุตัวตนแล้ว (ไม่ส่งชื่อลูกค้า/ที่อยู่/รูป)
- ใช้ free tier กับ **ข้อมูลสังเคราะห์/TEST_ONLY เท่านั้น** จนกว่าจะยืนยันเงื่อนไข (ดูด้านล่าง); ข้อมูลจริงต้องใช้เงื่อนไขที่ไม่นำข้อมูลไปพัฒนาผลิตภัณฑ์ หรือโมเดลที่โฮสต์เอง

## เงื่อนไข API ฟรี (ต้องยืนยันจากเอกสารทางการก่อนตัดสินใจ)

- **Gemini API free tier:** แหล่งข้อมูลรองหลายแห่งรายงานตรงกันว่า free tier ให้ Google นำเนื้อหาที่ส่งไปใช้พัฒนาผลิตภัณฑ์ได้ ขณะที่ paid tier ไม่ใช้; rate limit ต่ำและเปลี่ยนบ่อย ยังไม่ได้ยืนยันกับหน้าเอกสารของ Google
- **Web Speech API:** ฟรีแต่ขึ้นกับ browser และเสียงออกไปนอกระบบ (ข้างต้น)
- ราคา/โควตา/เงื่อนไขเปลี่ยนได้ → ให้ตรวจหน้า pricing, rate limits และ terms ปัจจุบันก่อนเริ่มเฟส 5

1. รายการกฎเฟส 1 ที่ต้องมี และกฎไหน "เตือน" vs "บล็อก"
2. ใครกำหนดขีดจำกัดค่าต่อหมวด (Survey Owner?) และเก็บใน reference-data หรือ template version
